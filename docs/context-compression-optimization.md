# 上下文压缩稳定性优化方案

## 1. 目标

本方案用于把 EveryTalk 的自动上下文压缩升级为可校准、可恢复、可持久化、支持工具循环，并能在官方 OpenAI Responses 渠道承接原生压缩状态的完整链路。

最终行为必须满足：

1. 用户照常发送消息，系统在发送前完成必要压缩。
2. 压缩期间复用执行状态底部抽屉，只显示“正在压缩上下文”的扫描高光状态。
3. 临时网络故障自动有限重试，用户无需重复发送消息。
4. 压缩失败保留用户消息，并显示经过分类的具体原因。
5. 上下文圆环显示当前活跃上下文，用量详情保留整轮累计消耗。
6. 应用重启后继续复用已经完成的压缩检查点。
7. 工具调用期间继续监控窗口，优先缩减旧工具输出。
8. 官方 OpenAI Responses 返回的压缩项作为权威状态原样传递。

## 2. 官方依据

实现参考：

- OpenAI Compaction 指南：https://developers.openai.com/api/docs/guides/compaction
- OpenAI Responses `/responses/compact` 规范：https://developers.openai.com/api/reference/resources/responses/methods/compact
- Codex CLI `compact.rs`、`compact_remote.rs`、`compact_remote_v2.rs`
- Codex CLI `session/context_window.rs` 与 `session/turn.rs`

采用的核心机制：

- 自动压缩阈值不得高于模型上下文窗口的 90%。
- 服务端返回的令牌用量优先，本地估算只负责发送前预测和新增内容增量。
- 活跃上下文和整轮累计用量分开保存。
- 压缩流必须收到明确完成事件，部分输出不能安装为检查点。
- 临时错误采用有限指数退避，认证和参数错误直接失败。
- 工具循环中优先替换低价值工具输出，保留调用对应关系。
- 压缩状态完成后一次性安装，失败时保持旧状态不变。
- 当前系统提示和工具定义每次重新构建，避免摘要携带陈旧配置。

## 3. 不直接照搬的部分

1. Codex 本地 20K 与远端 64K 的固定保留预算改为按模型窗口比例计算。
2. OpenAI 加密压缩项只在官方 Responses 地址启用。
3. Gemini、Anthropic 和普通 OpenAI Compatible 渠道继续使用本地摘要。
4. 压缩请求超窗时优先缩小分块，禁止静默删除尚未总结的用户原文。
5. 用户界面历史保持完整，压缩只改变模型可见请求状态。

## 4. 数据模型

### 4.1 请求上下文配置

`ChatRequest` 增加内部上下文管理配置，包含：

- 模型上下文窗口。
- 预留最大输出。
- 已钳制到 90% 以内的压缩阈值。
- 自动压缩开关。
- 官方 Responses 权威输入状态。
- 权威输入状态的估算令牌数。

该配置只供客户端构建请求使用，普通渠道不会把它作为未知字段发送给上游。

### 4.2 持久化检查点

AI 消息增加 `ContextCompressionState`，通过 Room JSON 字段持久化：

- 状态结构版本。
- 配置、渠道、模型指纹。
- 摘要与覆盖到的消息 ID。
- SHA-256 前缀指纹。
- 窗口编号、当前窗口 ID、前一窗口 ID。
- 压缩前后估算令牌数。
- 官方 Responses 权威输入 JSON。
- 权威状态覆盖到的 AI 消息 ID。
- 权威状态估算令牌数。

检查点在摘要完整成功后创建，并随预创建 AI 消息一起保存。Room 迁移只增加一个可空 JSON 列，旧历史无需转换。

### 4.3 令牌用量

同一 AI 消息保存两类用量：

- `tokenUsage`：整轮所有模型请求的累计用量，用于用量详情。
- `ContextUsageSnapshot.measured*`：最后一个请求轮次的活跃上下文，用于圆环和下一轮校准。

各直连客户端为 usage 标记工具循环序号，保证仅最终事件的渠道也能正确区分轮次。

## 5. 压缩触发与窗口算法

### 5.1 阈值

有效触发阈值：

```text
min(用户设置百分比, 90%) × 模型上下文窗口
```

发送前占用：

```text
本地输入估算 + 最近一次服务端输入校准差值 + 原生压缩状态估算 + 预留输出
```

正校准差值同时参与裁剪、超长输入压缩和最终超窗校验。负差值只用于触发预测，不能放宽模型硬上限。

### 5.2 最近轮次

- 默认尽量保留最近两轮和 25% 的上下文窗口。
- 会话只有两轮且需要压缩时，保留最新一轮，压缩第一轮。
- 会话只有一轮且当前用户输入超窗时，使用首轮超长输入分块压缩。
- 开启自动压缩时，通用窗口裁剪不得删除尚未进入摘要的旧轮次。

### 5.3 模型切换

检查点包含配置、渠道和模型。切换模型后：

- 本地摘要仍可在前缀指纹一致时复用。
- 服务端 usage 校准和 OpenAI 原生压缩状态只在模型指纹一致时复用。
- 新模型窗口更小时，发送前按新窗口立即压缩。

## 6. 压缩请求可靠性

### 6.1 完成校验

摘要请求必须满足：

- 没有收到结构化错误事件。
- 收到 `Finish` 或 `StreamEnd`。
- 最终文本非空。

流提前结束时，即使已经产生部分文本，也按失败处理。

### 6.2 错误分类

- 网络断开、408、409、425、429、5xx：最多重试两次。
- `context_length_exceeded`：缩小分块预算后重新切分。
- 401、403：直接报告认证失败。
- 参数错误、空摘要、模型拒绝：直接报告原始原因。
- `CancellationException`：立即向上传递。

退避间隔采用带轻微抖动的 500ms、1000ms。

### 6.3 自适应分块

压缩分块被服务商判定超窗时，分块预算按 75% 缩小，最多调整四次。每次调整从当前压缩轮次重新切分，禁止安装部分片段摘要。

## 7. 工具循环上下文治理

每次工具结果加入下一轮模型请求前执行：

1. 读取上一个模型请求的活跃 usage。
2. 估算新增工具输出。
3. 达到压缩阈值时，从最旧工具输出开始替换为短占位文本。
4. 保留工具调用 ID、工具名称、成功或失败状态及最新输出。
5. 单个最新输出仍过大时保留头尾并写入明确截断标记。
6. 发生缩减时发送“正在压缩上下文”执行状态，下一次内容到达后由现有逻辑清除。

该治理覆盖 OpenAI Chat、OpenAI Responses、Gemini 和 Anthropic 的内部工具循环。

## 8. OpenAI Responses 原生压缩

启用条件：

- 自动上下文压缩已开启。
- 实际请求地址主机为 `api.openai.com`。
- 当前请求使用 Responses 客户端。

请求行为：

1. 设置 `store=false`。
2. 添加 `context_management=[{"type":"compaction","compact_threshold":...}]`。
3. 收集 `response.completed.output` 或 `response.output_item.done` 中的完整输出项。
4. 工具循环必须把 function call、reasoning、message 和 tool output 一起传入下一轮。
5. 出现 `type=compaction` 后，只丢弃该项之前的旧输入。
6. 最终把从最近 compaction 项开始的权威输入 JSON 写入 AI 消息。
7. 下一轮从权威输入开始，只追加其覆盖点之后的新消息。

兼容处理：

- 官方端点返回明确的 `context_management` 不支持错误时，本轮关闭原生压缩并退回本地压缩链路。
- 自定义兼容地址不发送原生压缩字段。
- 权威压缩项禁止解析、改写或转成可读摘要。

## 9. 原子安装与恢复

1. 压缩前保存当前有效检查点。
2. 所有摘要片段完成并通过最终窗口校验后生成新状态。
3. 在互斥区内一次性替换内存状态。
4. 将同一状态附加到当前 AI 消息并强制保存历史。
5. 应用重启后，从最近一条匹配配置的 AI 消息恢复。
6. 前缀 SHA-256 不匹配时废弃本地摘要。
7. 模型、渠道或配置不匹配时废弃服务端权威状态。

## 10. 实施顺序

1. 增加数据模型、90% 硬上限和令牌轮次标识。
2. 修复活跃 usage、圆环同步与发送前校准。
3. 修复两轮会话压缩和通用裁剪保护。
4. 增加压缩流完成校验、错误分类、退避与自适应分块。
5. 增加工具循环输出治理。
6. 增加 Room 持久化检查点和恢复。
7. 接入官方 Responses 原生压缩和权威状态续传。
8. 完成相关单元测试、全量单元测试和 Debug APK 构建。

## 11. 验收标准

- 自动压缩阈值配置和运行时均不超过 90%。
- 两轮超窗会话不会静默丢失第一轮。
- 临时错误可自动重试，残缺流不能生成检查点。
- 分块实际超窗时会缩小后重试。
- 圆环使用最后一次请求的活跃上下文，累计 usage 保持正确。
- 四种工具循环都能在达到阈值时缩减旧工具输出。
- 应用重启后本地检查点可恢复。
- 官方 Responses payload 包含正确的 `context_management` 和 `store=false`。
- 原生 compaction 项原样进入下一次请求。
- 普通兼容地址不出现 OpenAI 专属压缩字段。
- 相关单元测试通过。
- 全量 `:app:testDebugUnitTest` 通过。
- `:app:assembleDebug` 成功。

## 12. 实施结果

以下项目已全部落地：

- 90% 压缩阈值硬上限、两轮会话切分和服务端输入校准。
- 首轮超长文本与文档提取后的分块压缩，真实超窗时按 75% 自适应缩块。
- 压缩流完成校验、明确错误分类、最多两次临时错误重试和指数退避。
- OpenAI Chat、OpenAI Responses、Gemini、Anthropic 四类工具循环输出治理。
- 活跃请求 usage 与整轮累计 usage 分离，原生压缩后圆环立即切换到当前活跃上下文。
- Room 12 压缩检查点持久化、11 到 12 迁移、SHA-256 前缀校验和重启恢复。
- 官方 OpenAI Responses 的 `store=false`、`context_management`、完整 output item 续传、compaction 权威状态裁剪和兼容降级。
- 执行状态抽屉中的“正在压缩上下文”扫描高光，以及压缩失败具体原因展示。

验证结果：

- 关键路径定向单元测试通过。
- 全量 `:app:testDebugUnitTest`：979 项，0 失败，0 错误，1 项按既有条件跳过。
- `:app:assembleDebug`：成功。
